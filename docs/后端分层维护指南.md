# 后端分层维护指南

适用工程：`handover-2026-10-24/RunRunCampusBackend`。两个应用按相同的职责原则组织，但不共享业务账号、数据库模型、接口或运行环境。业务定义仍以阶段一业务基线、专题规则及数据模型与接口契约为准。

## 目录与依赖

在 `com.zhangxuan.runrunv2` 与 `com.zhangxuan.runruncampus` 内分别组织：

|目录|维护职责|
|---|---|
|`controller/<模块>`|HTTP 路由、参数与认证上下文、状态码和响应头；调用 Service|
|`service/<模块>`|业务判定、权限、幂等、事务、状态推进、跨模块编排|
|`mapper/<模块>`|JdbcTemplate SQL、绑定参数和行映射；使用调用方事务连接|
|`repository/<模块>`|legacy 既有 JPA Repository；不新增无意义 Mapper 包装|
|`dto/request/<模块>`|请求字段、Jackson 和校验注解|
|`dto/response/<模块>`|对外响应和内部响应载荷；相关响应族可保留在小型容器中|
|`model/<模块>`|实体、数据库事实、领域值及快照|
|`enums/<模块>`|业务枚举；两个应用的同名枚举分别保留|
|`security`、`exception`、`config`|安全拦截、错误映射与应用技术配置|
|`integration/<渠道>`|微信、支付、推送及私有存储适配器|
|`task/<模块>`|仅注册调度并调用 Service，保留环境及功能门禁|
|`bootstrap`|受控初始化、启动校验及主机命令入口|

业务层不依赖 Controller 内嵌类型，持久化层不反向引用 Service。不要把两个应用的语义不同实现合并到大型 common 包。`BackendLayeringTest` 检查应用隔离、HTTP 与持久化依赖方向、Mapper 事务归属及调度注册位置。

## 从路由定位实现

在仓库根目录运行 `rg -n 'RequestMapping|GetMapping|PostMapping' handover-2026-10-24/RunRunCampusBackend/src/main/java` 定位路由，再沿构造器中的 Service 和 Mapper/Repository 字段查找。避免只搜索类名，两个应用可能有同名类。

例子：

* `POST /api/v2/orders` → `controller/order/OrderController` → `service/order/OrderService` → `mapper/order/OrderMapper`、`mapper/order/OrderStore`；原始应付写入继续通过 `OriginalPaymentWriter` 参与订单事务。
* `GET /api/v1/admin/orders/{id}/delivery-proof` → `AdminOrderDeliveryProofController`（原权限及 no-store/nosniff）→ `AdminOrderDeliveryProofService` → `OrderRepository`、`OrderProofRepository` → `OrderProofStorage`。文件路径不进入响应 DTO。
* legacy 管理工作台 → `AdminCommandCenterService` → `AdminCommandCenterMapper`。Service 保留重复读快照和权限筛选，Mapper 保留队列 SQL 和原始计数。

`docs/reports/backend-layered/mapping.md` 列出全部基线主类映射；`after.json` 和 `dependencies.json` 可用于核对当前目录及类依赖。

## 运行与验证

Java 17、Maven 3.9、Docker 和 PowerShell 7 是当前验证工具。以下 Maven 命令在后端目录执行：

```powershell
mvn -B -ntp clean test
mvn -B -ntp -Pv2-identity -DskipTests package
pwsh -NoProfile -File tools/run-v2-isolated-tests.ps1
```

默认主类为 `com.zhangxuan.runruncampus.RunRunCampusBackendApplication`，保留 legacy JPA/Flyway 和原数据库配置。只使用隔离的本地数据库运行 legacy；其旧 V1–V43 不改写，也不作为 v2 初始化入口。

`v2-identity` profile 主类为 `com.zhangxuan.runrunv2.IdentityApplication`。其组件扫描仅覆盖 v2 命名空间，并排除 JPA/Flyway 自动配置。默认 legacy 根包扫描不会包含 v2。不要扩大扫描至 `com.zhangxuan`，也不要为减少入口数量合并两个启动类。

v2 使用全新 `runrun_v2` schema。完整的隔离启动命令在仓库根目录执行：

```powershell
Copy-Item .env.v2-test.example .env.v2-test
pwsh -NoProfile -File tools/initialize-v2-environment.ps1 -ConfirmIsolatedTest
docker compose --env-file .env.v2-test -f compose.v2-test.yml up --build -d
pwsh -NoProfile -File tools/verify-v2-environment.ps1
pwsh -NoProfile -File tools/verify-v2-local-migrations.ps1
```

初始化脚本只生成被 Git 忽略的合成测试凭据，拒绝覆盖已有值。不要打印或提交环境文件。Compose 后端仅绑定本机 8082，数据库不发布端口；模拟渠道和测试管理员仍受既有门禁控制。验证脚本包含管理员登录、session、通知、资质列表、登出、私有存储卷权限和旧库哨兵检查。生产开放及真实支付不在本指南授权内。

隔离 runner 递归读取测试包声明并使用完整类名运行；移动测试后不能恢复成只匹配根包的平面通配符。现有真实数据库测试继续使用 PostgreSQL/Testcontainers，不以 mock 替换以获得通过。

## 新增代码约定

新增接口先对照技术契约，分别定义请求及响应类型，并保持错误码、JSON 严格校验、认证和权限规则。Controller 不直接操作数据库，也不把完整实体默认暴露为响应。

Service 方法承担业务事务。Mapper 不添加独立事务、不打开独立连接、不提交调用方事务。修改 SQL 时逐项核对锁顺序、WHERE 条件、版本、自增和幂等作用域；有状态竞争时补充真实数据库回归。Service 接口仅在确有替换或边界需要时添加。

Task 只调用 Service 代理，不移动或重复注册事务逻辑；新增调度同时检查 profile、条件 Bean 与数据库函数可用性。通知外部调用不得并入 claim/完成回写的长事务。

金额保持分和原舍入，流程版本与并发版本不能混用。保全优先于证据清理，不把未接入的凭证适配器当作真实证据。复杂方法注释解释事务、锁、幂等及安全约束的原因，引用规则文档，不逐行复述代码。

重构、业务修复和迁移分开评审；发现既有缺口单独登记。先运行受影响模块测试，再运行完整回归和隔离启动；不要删除测试、弱化断言或把环境阻塞标为通过。
