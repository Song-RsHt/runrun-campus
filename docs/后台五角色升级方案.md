# 后台五角色升级方案

版本：2026-10-25  
状态：后续升级参考草案、未实施、未验证；不作为阶段一验收依据，不参与当前规则优先级裁决。

## 1. 定位

阶段一 v2 采用一种管理员，具体以[数据模型与接口契约](数据模型与接口契约.md)和[阶段一业务基线](阶段一业务基线.md)为准。本草案用于以后多人协作时讨论分工，与当前契约冲突以契约为准，不自动生效。旧 v1 代码已有五角色不意味着生产已部署、已分配这些角色，也不意味着新后台现在必须复制它们。

阶段二真实资金上线前必须重新评估单人审核、金额分级及复核。本草案不是真实资金上线许可，未确认的阈值不填成“50元”等既定业务要求。

## 2. 已核对的旧代码事实

来源：交接后端 `admin/AdminRole.java`、`admin/AdminPermission.java`、V7、MFA服务及溯源核验服务；未连接生产库核对账号分布。

| 代码 | 角色 | 现有能力摘要 | 不能误读的边界 |
|---|---|---|---|
| SUPER_ADMIN | 超级管理员 | 现有全部枚举权限，含强制完成、审计、配置与资格相关管理 | 不代表每个旧管理员都有这些权限；v2资格仍须显式启用 |
| OPERATIONS | 运营 | 订单调度/归档、人工支付核款、溯源记录/查看、配置、骑手审核等 | 不含旧 ORDER_FORCE_COMPLETE；不能将“管理员可结案”直接挂到旧强制完成权限 |
| SUPPORT | 客服 | 订单/用户查看，问题与反馈登记处理 | 没有凭证溯源查看和骑手查看权限，不能宣称现状已能取证调查 |
| REVIEWER | 审核员 | 用户和骑手查看、骑手资质审核 | 不等于可审规格调整、退款或资金审批 |
| AUDITOR | 审计员 | 审计及部分业务查看，溯源查看和 PROVENANCE_VERIFY | 溯源核验写 verified_by/verified_at，且核验人与记录人不同；不能简单称为只读 |

## 3. 后续建议分工（未生效）

| 角色 | 建议职责 | 应保留的控制 |
|---|---|---|
| 超级管理员 | 管理身份资格、角色配置、例外授权和系统治理 | 不默认用来日常处理全部资金；资格变更审计、MFA |
| 运营 | 调查、调整审核、结案、定责、分配、冻解、退款赔付和付款操作 | 按明确动作授权，必要时金额分级/复核；不能绕过账本余额约束 |
| 客服 | 登记、联系、调查、提交处置建议 | 如承担调查，新增本案只读证据范围，限售后关联任务与订单、读取审计；否则调查交运营，不能仅靠菜单授予全库隐私读取 |
| 审核员 | 骑手资质审核及未来明确分配的复核任务 | 资质审核与调整、退款复核分别授权，不因名字相同自动获得资金权限 |
| 审计员 | 查看审计、账本与所需证据，核查留痕 | 业务只读与独立溯源核验写动作分开说明；保持记录人不得核验自己记录 |

需要单独定义的动作包括调整批准/拒绝、关闭未决调整按原价、长期结案转欠款、退款、赔付、分配批准、冻解、付款登记、免债及终止追偿。未来权限名和金额阈值须正式确认后写入契约与迁移，不直接复用旧 ORDER_FORCE_COMPLETE 解释所有结案。

## 4. 升级步骤与验收门槛

1. 核对实际部署角色、使用人数和职责；由项目所有者确认权限矩阵、金额阈值、复核人及值班责任。
2. 分开建模业务动作、数据范围与复核规则；旧账户迁移不得把客服/审计静默升权。v2资格与角色两者均由后端检查。
3. 先安排新迁移版本、扩展审计 action/target_type，再部署后端和菜单；更新唯一契约、业务规则及决策记录，明确本草案哪些段落转为生效规则。
4. 验证各角色正反例、越权、MFA、自己审批自己记录、撤权即时失效、证据范围、冻结及付款竞争；完成阶段二资金控制重评，才申请真实资金发布。

本次不改旧角色代码，不新增五角色数据库迁移，不提前启用金额分级或双人审核。
