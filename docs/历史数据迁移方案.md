# 历史数据迁移方案

版本：2026-10-25

## 1. 版本核对

生产迁移前先读取生产库 Flyway 历史，不假定当前版本。若实际版本为 V41，严格按 V42、V43 顺序补齐；之后新增迁移从 V44 开始。若不是 V41，必须先记录实际版本并重新制定顺序。

迁移前完成备份、校验和隔离恢复演练，未经单独书面确认不得执行生产迁移。

## 2. V44+ 目标

新增结构拆分履约状态、业务支付单及尝试、调整单、凭证、交接/重新履约任务、结算账本及调整、独立欠款和通知。新小程序通过 `/api/v2` 使用新结构；不覆盖原报价、原支付或原分账。

### 流程隔离与一致性

- `order_flow_version` 建单确定、不可修改；新表只放新流程订单相关行，不将历史订单回填到新流程表。旧行保留旧版本含义（必要时只增加旧版本标记，不重算历史业务）。
- v2 新订单落独立 `v2_orders` 表；旧 `campus_orders.status` 仅由 v1 在历史订单收尾时更新，不存新订单兼容行，不作为 v2 事实来源，禁止双向状态同步。混合列表使用只读 UNION ALL 投影和统一游标，见契约 S01。
- 若新主状态与原款支付状态在同表，可增加单向 CHECK；分表时不能声称存在跨表 CHECK，使用事务、锁、条件更新保证“原款成功→待接单”原子转换。主状态待支付不得对应 PAID，反向不限制其他合法状态。
- 原款支付单按订单唯一；补款单按调整单唯一；尝试另表。原款与补款不可被过宽“订单＋用途”约束错误合并。定时对账（至少每日）检查幽灵待支付、重复成功、退款和结算汇总；修复须有事件和审计。

### 配套目标表和字段

- `delivery_zones`：code、名称、包裹加价分、启用状态；初始 STANDARD 0、MEIYUAN 200。新订单结构化选择，服务端校验、留报价快照。
- 服务点配置：代码、名称、经纬度、坐标系、启用状态；运营核实实际坐标后录入，不编造。订单留取件点坐标及配置版本快照；距离比较采用统一坐标系。
- 定位事件：订单、履约任务、骑手、类型（到场/送达）、坐标/坐标系、服务器接收时间、采信结果和原因；客户端时间仅辅助，不作为取消前打卡依据。重试有请求标识，选定有效事件，不覆盖。
- `delivered_at` 保存实际送达；独立保存确认起点、截止时间及失效事件。调整审核时间、补款提示截止、审核升级和欠款结案分别保存，不能混用送达时间。
- 调整单可升级人工，不自动拒绝；超时消息、负责人指派、决定、拒绝和转欠款可审计。履约任务结束与订单最终完成分别记录。
- 欠款、还款、正式停止追偿、证据保全理由及定期复核独立记录；结案不删除欠款。站内消息和微信发送/重试任务持久化，业务提交与通知任务可靠衔接。

### 配置及生效规则

| 配置 | 默认值 | 语义 |
|---|---:|---|
| pending_payment_minutes | 30 | 原款订单付款期限 |
| delivery_confirm_minutes | 10 | 可确认后完整窗口 |
| arrival_radius_m | 100 | 到场距离上限 |
| arrival_window_minutes | 30 | 取消前有效打卡时间窗 |
| arrival_subsidy_cents | 100 | 平台额外补贴 |
| adjust_pay_timeout_minutes | 15 | 补款提示/一般售后处理期限，不自动取消 |
| adjustment_review_remind_minutes | 120 | 两小时提醒 |
| adjustment_review_escalate_minutes | 1440 | 24 小时升级人工 |
| overdue_debt_closure_days | 30 | 补款逾期后可人工结案阈值 |

上述数值进入 `platform_settings` 的新增配置，负责人须配置并校验有效权限；结构化营业时段为 Asia/Shanghai 每天 [09:00,23:00)，不能从旧 business_hours 展示文本解析。旧 wait_minutes 和 issue_pending_minutes 等保留原语义，不能冒充新审核或确认期限。

配置变更记录审计；已生成订单报价、期限、补贴判定和确认窗口采用保存的快照，不追溯修改。生产 v1/v2 建单开关默认关闭，模拟通道生产启动强制禁用。

## 3. 历史兼容

旧订单、旧收货码、旧人工收款和旧退款任务保留到结清；新订单不生成或校验收货码。旧 Android 只允许查询、履约收尾和支付退款结清。

## 4. 数据保留

本节统一规定照片、精确位置及定位事件删除；普通期限不能覆盖争议、欠款追偿的必要保全。

| 数据/情形 | 期限 |
|---|---|
| 学生证 | 审核后 30 天 |
| 普通无争议履约照片、精确位置 | 订单完成后 7 天 |
| 待补款送达证据 | 结清后 7 天；仍待补款继续保存，满 30 天提醒负责人处理 |
| 争议或欠款追偿必要证据 | 不因结案删除；欠款结清或正式终止追偿，且相关争议全部结束后再保留 7 天 |
| 到场补贴证据 | 审核和补贴结算均结束后 7 天 |
| 未申请补贴的到场证据 | 订单结清或结案后 7 天；争议/追偿需要时顺延 |
| 核心交易、支付退款、独立欠款、售后、结算及审计 | 至少 3 年 |

保全理由、负责人、复核日期及解除条件落库，定期复核必要性，不用一句“欠款”永久无审查保存全部隐私。删除任务先检查保全标记，删除文件及精确位置正文并撤销访问，保留必要删除审计和核心事件摘要。已删除不能重新生成假凭证；结案后还款只解锁尚在保留期的资料。

## 5. 上线顺序与审计白名单

核对 V29、V43 及之后实际历史里的 `admin_audit_logs_action_check` 和 `admin_audit_logs_target_type_check`，在新增迁移中同时扩展。范围覆盖调整审核/升级/结案、退款、冻结/解冻、付款登记、交接/重新履约、账号迁移、欠款追偿和凭证保全删除。应用枚举、目标类型、数据库约束及测试同步，不能只加 action。先迁移扩容，再部署写新动作的代码；不得改已执行 SQL。

## 6. 迁移数据核对

迁移前留基线、迁移后逐项比较：账号数和角色、订单数及版本/状态分布、原价/已付金额、支付成功和退款在途/完成汇总、调整单与欠款余额、平台/骑手分账及付款/冻结余额、凭证数量与文件对应、审计摘要和 Flyway 校验和。新表仅有新订单行，历史订单能够继续通过 v1 收尾，v2 不静默读取旧版本。

金额用分并检查守恒；抽样覆盖历史人工收款和旧退款任务。无法解释的数量、金额或权限差异必须阻止发布，先排查，不用批量改数据“对齐”。

## 7. 回滚

迁移失败时停止后续版本，保留失败日志和数据库备份；先在隔离环境恢复验证，再决定修复迁移或回滚。不得直接修改已执行迁移文件。

## 8. 预留迁移版本与模型权威

字段、约束、索引、接口映射统一见[数据模型与接口契约](数据模型与接口契约.md)；本节只管理版本、依赖和核对。V44–V47 为本方案预留，禁止并行开发者各自重复占号；创建前核对实际库及迁移目录，已被占用则停止并更新分配记录，不覆盖旧脚本。

| 版本 | 分工 | 必须一起具备的约束 |
|---|---|---|
| V44 | 独立新订单、任务、交接、凭证、定位事件、售后、微信绑定、基础配置、区域/服务点、保全/删除审计、v2管理员启用标记与安全版本；共享旧资质表并发版本与照片资源标识增量、资质审计事件 | 流程版本不可变、并发版本从0递增；管理员默认不启用及首次启用审计；资质新旧入口共享锁与增版；证据清理支持无订单的资质资源，不等 V47 |
| V45 | 调整、支付单/尝试、退款、欠款/还款、幂等记录 | 原款按订单、补款按调整单唯一；欠款只依订单及主体，不引用尚不存在的冻结表 |
| V46 | 骑手分配、账本、冻结及变更、逐单付款登记 | 冻结强制校验；多案不早释；如需欠款关联冻结，在本版后加引用，不能让 V45 前置引用 |
| V47 | 通知/outbox、配置管理增量及剩余审计权限支持 | 复用 V44 基础配置表，不重建；可靠站内与尽力微信；升级负责人有效 |

每个版本同时扩充本版动作所需 action 和 target_type CHECK，先迁移后部署代码；不能等到 V47 才补前序审计白名单。完整业务联调在四版依赖齐备后进行，预留号段不是已执行迁移证明。

清理必须在删除时重新检查所有保全、争议、待补款与追偿条件，删除任务和新保全共用订单锁及排他执行机制；存储失败记录重试，不伪记已删。保全记录可多来源并存，保留创建/复核/解除，删除审计不复制敏感正文。具体期限继续以第 4 节为准。

## 9. 开发规则修订迁移约束

流程版本固定为新单版本，不得把通用并发版本也固定为2。新旧订单隔离和历史不回填新流程表的约束继续适用；共享旧资质表属于账号资格兼容，不属于迁移历史订单。

V44对现有资质表增加并发版本及稳定照片资源标识，保留既有账号接单资格、申请状态、照片与审核事实；不重新采集姓名/学号/学校，不启用旧有效期列。具体字段、照片资源初始化及只追加审计事件以契约M44-15/M44-16为准。应用部署必须同时让v1/v2申请、照片替换、审核与清理共用锁并递增版本，不能只给v2加版本而放任v1旁路写入。新增动作及目标白名单先迁移扩容再部署。

保全/删除模型支持订单或资质恰一主体；学生证清理不伪造订单外键，旧照片替换仍保留可审计、可重试的资源引用，保全与清理按资质排他。第4节所有保留期限保持不变，照片删除不撤销既有接单资格。骑手混合历史仅做授权后的只读投影，不为v1补造新任务行。

迁移核对另检查资质申请数/状态、已批准账号数、照片资源引用及并发版本初始化；任何资格静默丢失、旧照片提前删除、历史订单进入新表或无法解释的引用差异均阻止发布。本次仅预留设计，不执行迁移或改写已执行脚本。
