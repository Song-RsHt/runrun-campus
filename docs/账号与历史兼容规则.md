# 账号与历史兼容规则

版本：2026-10-25

## 1. 阶段一微信身份

阶段一小程序使用真实 AppID 和微信身份能力：客户端通过 `wx.login` 获取 code，后端调用 `code2session` 获取 openid，并通过 `getPhoneNumber` 验证手机号。openid 与 AppID 的唯一关系只能由后端建立，不能信任前端传入的 openid。

微信手机号是主登录方式。一个微信身份只能绑定一个平台账号，一个账号在同一 AppID 下不能绑定冲突身份。

## 2. 旧账号恢复

普通用户可用验证手机号恢复同手机号旧账号；绑定后微信登录和密码登录均可用。原密码或已登录旧会话可作为辅助验证。手机号不一致、账号冲突或无法通过已确认渠道证明归属时转管理员；普通账号旧会话失效本身不否定重新验证同手机号后的自助恢复。

骑手和管理员不得通过普通手机号流程自动恢复，必须人工核验。注册仍可选择普通用户或骑手，骑手审核通过后才能接单。新注册骑手可获得未审核账号和登录会话，自行申请资质并上传学生证；仅匹配到旧骑手/管理员账号时进入人工恢复，不能把新注册也拦入恢复流程。迁移、绑定、解绑和冲突处理必须记录审计。

## 3. API 和历史订单

新小程序使用独立 `/api/v2`。`/api/v1` 只服务历史 Android 订单、历史支付退款和在途事项收尾。Android 立即禁止创建新订单；历史订单可查询、履约收尾和结清旧支付/退款任务。

旧账号的密码、旧订单的收货码、旧支付方式、人工核款记录和历史字段只作兼容保留，不能作为新订单流程。

## 4. 客户端退场与错误契约（目标）

生产阶段一 v1、v2 均停止新建订单，历史查询、履约和支付退款保留。v1 新建单返回 HTTP 410，响应为 `{"code":"V1_NEW_ORDER_DISABLED","message":"旧版下单已停止，请关注平台恢复通知"}`；保留 message 供旧客户端展示，不能依赖客户端升级才阻止下单。测试环境仅按配置开放 v2。生产开放由阶段二发布安排另行授权，不通过开模拟支付恢复。

`order_flow_version` 在建单时写入且不可修改，旧数据标记方式见[历史数据迁移方案](历史数据迁移方案.md)；v2 请求历史订单明确拒绝，不静默兼容，不把历史查询也关闭。

错误体、错误码、混合列表与版本检查统一引用[数据模型与接口契约](数据模型与接口契约.md) A01、S01、E01；本专题不维护重复码表。

v2 业务错误统一 code、message，客户端以 code 分支、以 message 提示；权限校验先于资源细节响应，不能通过版本或凭证错误泄露他人订单。当前异常处理仅 message，以上为待实现契约。

## 5. 微信前提和账号验收

真实身份只在具有小程序主体、手机号组件权限、合法测试域名及 AppSecret 受控托管条件时验收。不能信任手填手机号或前端 openid 冒充微信验证。账号注册、恢复、重复绑定、骑手审核、管理员不能自助恢复及历史归属验收见[本地开发与验证](本地开发与验证.md)。

## 6. 阶段一后台与新客户端组织

阶段一 v2 只有一种业务管理员，所有旧管理员默认不启用 v2。V44 在账号中增加启用标记和安全版本；首次及后续启停只能由项目所有者指定的受控部署身份或既有 SUPER_ADMIN 执行并审计。普通 v2 管理员不能授权自己或他人。停用后后端立即拒绝已有会话的 v2 管理请求。

现有管理端新增独立 `/v2-admin` 模块和路由，校验 ADMIN 身份及启用标记，不沿用旧岗位菜单授权；资格管理入口另校验受控身份。旧 v1 角色、强制完成和溯源核验限制不变。阶段一单人、无金额分级只用于模拟资金，真实资金上线前必须重评。

现有小程序工程内新增独立 v2 分包、请求模块和会话存储；保留历史页面，不能让其调用新流程写接口。v2 会话使用 `runrun_session_v2`，不静默复用旧 `runrun_session_v1`。构建脚本根据显式 test/production 目标生成环境常量文件，缺失域名时构建失败，不回退生产；生成文件不手改提交。测试构建禁止生产域名，生产构建禁止测试域名和模拟支付控制入口，微信合法域名配置必须匹配。具体测试域名未提供，取得受控配置前不得声称真机验收通过。

历史混合展示必须结合支付方式、支付进度和旧主状态：货到付款、人工收款未付不能误显示为 v2 待支付；异常组合标待核查。统一映射在契约 S01，生产实际组合仍须统计，不能只看代码宣称没有异常数据。

## 7. 骑手任务、资质与共享资格

新小程序可查询骑手本人任务及合并的v1/v2历史。未获接单资格不妨碍读取自己的资质和既有历史；列表不会因此开放接单、接受任务或履约写入。旧订单详情只读，按可证明的本人履约关联授权，不根据姓名/手机号猜测归属，不暴露其他骑手证据和结算明细。

v2补齐资质查询、申请/重申请、学生证上传及启用管理员的查看/审核，复用原资质事实、存储及接单资格，不新增第二套审批记录。沿用照片审核，不新增姓名、学号、学校或有效期要求；状态与接单资格分开返回，既有已批准骑手重新申请保留资格。学生证删除不等于撤销资格。

新旧接口必须使用同一资质服务、锁与并发版本；旧入口换图或审核同样使新后台旧版本失效。学生证私有存储，受控读取禁止缓存并留审计；只允许本人的待审申请上传本轮照片，批准必须基于本轮有效照片。保留期限继续按迁移方案，保全优先、失败重试；旧v1照片清理不得绕过共享服务。唯一技术定义见[数据模型与接口契约](数据模型与接口契约.md)M44及A36–A40，以上均为待实现规则。
